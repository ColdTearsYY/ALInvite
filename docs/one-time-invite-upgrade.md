# 按权限组发放的一次性邀请码：升级与验收

本文对应 ALInvite 2.2.0 的一次性邀请码机制。代码构建完成不代表已部署到生产服；上线前须在数据库副本和测试服完成以下验收。

## 默认规则

| LuckPerms 组名 | 发放方式 | 累计在线时长间隔 | 未消费库存上限 |
| --- | --- | --- | --- |
| `default` | 循环发放 | 48 小时 | 1 |
| `vip1` | 循环发放 | 24 小时 | 2 |

小时数和库存上限可在 `config.yml` 的 `invite_quota` 中调整。按实际权限组名称匹配，继承多个匹配组时使用配置优先级最高的规则。未匹配或未安装 LuckPerms 时使用默认规则。

```yaml
invite_quota:
  enabled: true
  check_interval: 300
  fallback_group: default
  groups:
    default:
      mode: RECURRING
      hours_per_slot: 48
      max_codes: 1
      priority: 0
    vip1:
      mode: RECURRING
      hours_per_slot: 24
      max_codes: 2
      priority: 10
```

`max_codes` 计算可用码和预留码的总数；0 表示不限。旧版 `grant_mode`、`hours_per_slot`、`max_slots` 顶层兼容字段保留，但不再决定新的发放规则。已有配置只补缺失项，不清空服主设置。邀请码发放不依赖自动老玩家功能，也不要求额外授予 `alinvite.veteran`；合法准入玩家凭库存使用 `/code` 和 `/add`。

每个邀请码只接受一名玩家成功绑定。使用后永久失效；下一次达到条件时获得新的码，旧码不会重新启用。`/alinvite code` 查看当前可用码；查询命令本身不会额外赠送资格。

发放按累计在线时长节点计算：普通组为 48、96、144 小时；赞助组为 24、48、72 小时。满库存时跳过当期收益并持久化进度，不积累待领取余额。已使用后不重新开始计时。

累计时长现在由插件内置记录，默认每 30 秒保存，并在发码前主动刷新。单服用 SQLite，跨服共享 MySQL，按 UUID 合并在线区间，不依赖外部时长变量。查询命令、变量、历史时长衔接与异常停机边界见[内置时长说明](builtin-playtime.md)。`mode: ONCE` 可改为仅第一个时长节点发放；满库存时该唯一机会也会跳过。

`/alinvite add <玩家名>` 占用同一份邀请码资格。预留不能用于普通手动绑定，并计入容量。新建预邀请默认创建后 **20 个自然小时**过期，离线照常计时；取消或过期只退回该原码，成功认领不返还。普通可用码不受此期限影响，历史无期限记录保持原状。管理命令、期限配置、奖励恢复和人工核对见[稳定性运维说明](stability-operations.md)。

身份升降级会保留已取得的码和计时进度，不重发过去的时长收益。切换时先结算旧规则，再以当前累计时长建立新规则基线，从新规则的下一个节点继续发放。降级后库存超过新上限的，保留既有库存，停止新增，直到库存低于新上限。

隐藏开放注册池维持原规则：后台自动领取、不显示码、不建立邀请人关系，不消耗个人一次性码；已获隐藏注册资格的玩家仍可绑定朋友的一次性码。

## 旧数据处理原则

迁移须幂等执行，同一玩家重复登录或服务端重启不能重复转换库存。

- 保留历史邀请关系、累计统计、奖励记录和已绑定邀请码字段。
- 保留旧码、旧名额和旧领取阶段的迁移快照，便于对账。
- 旧固定码永久退出可绑定列表，不能在获得新资格后再次使用。
- 旧可用名额转换为不同的一次性码。超过新上限的历史库存保留，不额外补发。
- 已有预邀请保留目标和归属，并绑定独立的预留码。
- 旧账户首次使用新发放规则时，以实际读到的累计在线时长建立基线，避免把旧版以前的在线时长重新兑现。旧库存转换与该基线相互独立。

## 上线步骤

1. 停止共享同一数据库的所有 ALInvite 后端服，避免新旧版本同时写库。
2. 备份整个 `plugins/ALInvite/` 和数据库。SQLite 在停服后复制数据库及相关文件；MySQL 使用一致性备份，并确认可恢复。
3. 在数据库副本上试运行新版本，检查启动日志、组规则和抽样迁移结果。保留对账记录。
4. 确认 LuckPerms 中真实组名为 `default`、`vip1`；按需要调整间隔、上限和优先级。
5. 所有需要计时的后端安装相同版本和规则配置，保持 MySQL、表前缀以及代理转发 UUID 一致。内置计时会汇总各后端的在线区间；Redis 仅用于既有公告/缓存同步，不是计时依赖。不要混用外部时长版本与内置时长版本。
6. 启动并执行下列验收。通过后再放开正常入服。

若新版本运行后要回滚，必须将插件、配置和数据库一并恢复到升级前的一致备份。仅替换回旧 JAR 会让旧固定码逻辑重新运行，且旧版不认识新码库存。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 新普通玩家达到 48 小时 | 获得 1 个新码 |
| 普通玩家库存已满，跨过 96 小时后再使用旧码 | 不立即补发 96 小时的收益；等待下一个节点 |
| 新赞助玩家达到 24、48 小时 | 可持有 2 个不同的邀请码 |
| 赞助玩家库存为 2，跨过 72 小时 | 库存仍为 2，无待领取余额 |
| 一个码两人同时绑定，包括跨服提交 | 仅一人成功，关系和奖励只产生一次 |
| 旧码使用后重新获得新资格 | 旧码仍然无效 |
| `/alinvite add` 与手动绑定争用最后一个码 | 只有一种途径成功 |
| 预邀请目标认领失败或重复触发释放 | 仅退回一次；数据库临时错误不撤销预邀请 |
| `vip1` 到期，已有 2 个未消费资格 | 保留 2 个；普通规则不再补充，直到低于上限且到达新节点 |
| `default` 升级 `vip1` 后又降级、重新升级 | 不重复兑现同一时长阶段 |
| 旧数据迁移后重启、重复登录 | 不重复转换；历史邀请关系不变 |
| Folia 26.3 玩家跨区域移动、绑定与查询 | 无实体线程归属错误；数据库工作不阻塞区域线程 |

本地真实 MySQL、两台 Folia 后端和恢复验证的实际记录见[稳定性验收](stability-validation.md)。生产同款 LuckPerms、代理认证与正版/皮肤站身份连续性仍须按该记录列出的边界验收，不能从隔离测试推定。

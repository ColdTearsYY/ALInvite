# ALInvite 2.2.0：预邀请与工作恢复运维说明

本说明适用于本地 2.2.0 稳定性版本。插件未因此自动发布或部署。规则、历史库存迁移与内置时长分别见 [一次性邀请码升级](one-time-invite-upgrade.md) 和 [内置在线时长](builtin-playtime.md)。本轮实际证据见 [稳定性验收记录](stability-validation.md)。

## 邀请码和预邀请

默认实际组 `default` 每累计在线 48 小时获得一个码，容量 1；`vip1` 每 24 小时一个，容量 2。AVAILABLE 和 RESERVED 共同占容量。满库存跨过的节点永久跳过，使用或退回邀请码均不会重置累计时长，也不会解锁过去跳过的奖励。

手动绑定、预邀请预留和认领都先在同一事务中，以共享 MySQL 已提交时长和最近确认的组规则结算库存，再进行状态转换。即使邀请者离线或位于另一后端，也执行这一步。例如普通组在库存满时已达到 96 小时，另一服使用其旧码后，下一次额度检查不会补发 96 小时的码，下一个节点是 144 小时。

`/alinvite add <玩家名>` 从可用库存预留一个码，默认在创建后 **20 个自然小时**过期，离线时间照常计算。截止时间在创建时保存，到达该时刻即不能认领；清理任务稍后将原码退回 AVAILABLE。取消也退回同一个原码，重复取消、重复清理和认领竞争不会增加额外库存。成功认领后不返还。

普通 AVAILABLE 码不受这个 20 小时期限影响。历史预邀请没有截止时间的，保持无限期；修改配置或重启不会重算已保存的截止时间。重新创建同名预邀请会获得新的独立记录身份，旧请求不能取消或认领它。

在线新人仍在绑定宽限期时，也可由邀请人执行 `/alinvite add` 当场完成绑定。同服立即触发检查，共享 MySQL 的另一后端每秒检查待认领记录；原倒计时不重置。具体边界和跨服条件见[宽限期在线邀请](live-add.md)。

```yaml
pre_invites:
  expiry_hours: 20
  cleanup_interval_seconds: 30
delivery:
  retry_interval_seconds: 15
```

`expiry_hours: 0` 只关闭之后新建记录的期限；负数或非有限值回退到 20 小时。清理和恢复扫描间隔最少 5 秒。清理需要数据库可用和至少一台后端运行；全服停机期间自然期限仍会经过，再次运行或尝试认领时会识别过期。以数据库公共时钟计算期限，各后端应共享同一数据库并维护可靠的数据库时间。

## 玩家和管理员命令

以下命令都可使用既有别名 `/ali`、`/invite`。个人查询只访问执行者自己的 UUID，不能通过附加他人的名字切换对象。

| 命令 | 用途 | 权限 |
| --- | --- | --- |
| `/alinvite code` | 查看可用一次性码 | 既有 use/准入规则 |
| `/alinvite add <目标名>` | 为宽限期内的在线新人完成邀请；离线时预留原码 | 已准入、具有 use 权限和可用库存 |
| `/alinvite time` 或 `playtime` | 刷新并查看已提交在线时长 | `alinvite.use` |
| `/alinvite status` | 最近确认组、模式、累计时长、可用/预留/容量、下一节点及剩余时长 | `alinvite.use` + `alinvite.status` |
| `/alinvite pending` | 查看自己的预邀请目标、归属、创建和截止时间 | `alinvite.use` + `alinvite.pending` |
| `/alinvite cancel <目标名>` | 取消自己的预邀请，返还原码 | `alinvite.use` + `alinvite.pending` |
| `/alinvite deliveries` | 查看自己的持久化工作与状态 | `alinvite.use` + `alinvite.delivery` |
| `/alinvite admin status <UUID/已知名>` | 查询指定玩家规则和库存 | `alinvite.admin` |
| `/alinvite admin pending [UUID/已知名]` | 查询指定玩家或全部预邀请 | `alinvite.admin` |
| `/alinvite admin cancel <目标名>` | 取消指定预邀请 | `alinvite.admin` |
| `/alinvite admin deliveries [UUID/已知名]` | 查询指定玩家或全部工作 | `alinvite.admin` |
| `/alinvite admin delivery show <ID>` | 查看收件人、状态、保存的奖励定义及错误 | `alinvite.admin` |
| `/alinvite admin delivery retry <ID> <原因>` | 将已核对的 REVIEW 工作明确放回队列 | `alinvite.admin` |
| `/alinvite admin delivery done <ID> <原因>` | 将 REVIEW 工作人工确认完成 | `alinvite.admin` |

三个新增个人权限默认 true，管理员权限默认 OP。门禁中的玩家不能使用取消/处理命令绕过准入；查询不会创建库存或奖励。目标名为 3–16 位字母、数字和下划线。管理员名字解析只接受在线玩家或共享已知玩家目录，不根据离线名字猜测 UUID；不确定时使用后端实际收到的 UUID。

预邀请列表最多显示 50 条，工作列表显示最近 50 条。管理员需要更多历史时，可只读查询带相同表前缀的 `pending_invites`、`delivery_outbox`、`delivery_audit`。时间按 `time.timezone` 显示，并带时区。

`status` 报告最近可靠确认的组及其规则。离线玩家的 LuckPerms 组变更要等后续可靠观察确认，不能把旧快照当作实时组查询。未知规则、尚未注册、满容量、ONCE 已结束、待结算等状态分别提示。下一节点是累计时长节点，不是“消费后再等 24 小时”；当前容量为满时，显示节点也不意味着届时一定补发。未安装 LuckPerms 使用 fallback；已安装但暂时无法可靠读取用户组时会延后确认。

默认菜单展示内置时长并提示上述查询入口。内置菜单变量支持 `{playtime}`、`%playtime%` 及既有渲染写法；PAPI 使用 `%alinvite_playtime%`。完整库存与规则以 `status` 为准。升级合并保留用户已有语言和菜单列表，请对照新默认文件更新 `commands.help`、`commands.admin.help`、`commands.add.success`、`errors.invite_quota_exhausted` 及菜单说明，删除旧的固定 24 小时恢复承诺。

## 绑定后工作如何恢复

绑定关系、单次码消费及其应发礼包/白名单工作在同一个事务提交。里程碑领取标记与持久化父任务也一起提交；父任务确认后，逐项奖励和父任务完成记录再次一起提交。每个奖励独立记录，因此三项成功、一项失败时，只恢复未完成项。

工作保存创建时的奖励定义、数量、点券接口类型和命令模板。配置重载不会改变已欠的奖励。旧绑定没有可靠送达证据的，不批量补发；原有领取历史不清空。

| 状态 | 含义与处理 |
| --- | --- |
| READY | 等待玩家在线、依赖恢复、库存空间或下一次扫描 |
| CLAIMED | 某执行者已持有短期租约，尚未开始外部效果；超时可重新排队 |
| RUNNING | 已允许执行；进程中断后需按操作是否可安全重试处理 |
| DONE | 适配器确认成功，或管理员带原因确认完成；终态不自动重放 |
| REVIEW | 结果不明、配置无效或事件明确拒绝；等待管理员核对，默认不盲目重发 |

普通租约为 60 秒，调度执行窗口为 25 秒。独立领取令牌与条件更新限制正常并发执行者，已失效的执行者不能确认新租约的工作。安全操作超时会恢复 READY；不能确认外部效果的 RUNNING 工作转 REVIEW。无法在数据库与任意第三方插件之间实现分布式原子提交，因此不承诺崩溃边界上任意外部操作绝对恰好一次。

| 奖励类型 | 本插件如何判断结果 |
| --- | --- |
| 原生物品 | 玩家实体线程先核对背包空间；空间不足不发放并等待。添加后无剩余项才确认；部分添加或异常进入 REVIEW |
| Vault 金钱 | 未找到接口/提供者则等待；依赖返回 `transactionSuccess()` 为 true 才确认，明确失败可重试；调用抛错或无法读取结果需核对 |
| PlayerPoints 点券 | API 不可用时等待；`give(UUID,int)` 返回 true 确认、false 重试，无可验证返回值进入 REVIEW |
| 自定义点券/其他命令 | 全局调度器使用控制台分发；true 只表示分发获确认，不代表第三方业务已到账；false 或异常保守进入 REVIEW |
| 里程碑父任务 | 触发既有事件，允许后原子建立逐项子任务；取消进入 REVIEW。第三方事件监听器自行产生的效果不在本插件保证范围内 |
| 默认原生白名单 | 用后端实际 UUID 登记并读回确认，可安全重试；记录绑定时的后端 ID，允许该后端在玩家离线时完成 |

默认 `whitelist_on_bind.command: "whitelist add {player}"` 会使用 UUID 原生接口。其他自定义命令按普通命令的保守规则执行，支持 `{player}`、`{uuid}`。服务器 ID 必须唯一且稳定：已有白名单任务属于创建它的后端，不能靠改 ID 或在别服重试来转移任务。独立后端的原生白名单不是共享白名单服务。

隔离运行实测：已注册命令的处理器返回 false 时，`Bukkit.dispatchCommand` 仍可能返回 true。因此命令任务的 DONE 只能证明分发获得确认，不能作为第三方入账凭证；未知命令返回分发失败时会进入 REVIEW。

处理 REVIEW 前先用 `show` 查看保存的定义，核对对应插件余额、物品、命令日志等外部证据。已完成则 `done <ID> <原因>`；确认未生效且可以重新执行则 `retry <ID> <原因>`。两种动作都记录操作者 UUID/console、原状态、原因和时间。READY、RUNNING 和 DONE 不能通过这两个命令随意重置。

## 升级、备份与回滚

1. 停止共享此库的全部旧版后端，备份全部插件配置和一致数据库快照。先在副本核对既有关系、旧绑定码、迁移审计、可用码、预付预邀请和奖励历史。
2. 统一安装本版本，核对实际 `default`/`vip1` 规则、相同表前缀、各服唯一 `serverid`、共同 UUID 来源。MySQL 表需为 InnoDB；启动迁移由数据库命名锁串行执行。账号必须具备建表、索引、ALTER 及相关读写权限。
3. 本版增加持久化容量、预邀请截止时间/记录身份和工作/审计表；保留旧库存，旧无期限预邀请不追溯过期。迁移时保留旧可用名额及独立预付预邀请，允许历史库存暂时超过新容量。
4. 启动后检查日志及 `admin status`、`pending`、`deliveries`；对照已知数据验证，核对 REVIEW 原因。不要把历史工作一律标 DONE 或强制重发。
5. 回滚必须恢复同一时点的 JAR、配置和完整数据库。仅降级 JAR 会混用旧固定码与新库存/工作状态。若升级后已发生外部奖励，恢复旧数据库前还需对照审计处理这些外部效果，避免丢失记录后再次发放。

本轮不修改商店购买、返利体系、第三方事件实现，也不提供全服背包同步。正常关闭会补存在线尾段；断电或长时间数据库故障仍可能损失最后一次提交之后的在线时间，详见内置时长说明。

## 白名单与生产身份验收

原生 `white-list=true` 在游戏加入事件前拒绝未列入的账号，ALInvite 的门禁、预邀请、隐藏注册无法绕过它。首次入服需要接待后端、代理层准入或运营侧预先放行；绑定后的白名单工作服务于后续连接。

隔离测试使用离线模式协议客户端，测试 UUID 来自后端真实登录事件；它不能证明 Velocity/MultiLogin、正版认证或 `skin.windmc.top` 皮肤站链路正确。生产上线需分别准备正版与皮肤站测试账号，经实际代理登录 A、正常切换 B、退出重登，逐次核对后端 UUID、共享邀请关系、计时会话与额度节点。禁止按名字重新推导/合并生产账号。还应在生产同款 LuckPerms/Vault/PlayerPoints 版本的隔离副本上核对组变更和真实入账。
